# Раздел I. Разработка ИС

## 1.1. Понятие информационной системы, виды ИС

*Фото 1. Методичка, с. 4–5.*

**Информационные системы (ИС)** — компьютерные системы, ориентированные на обработку данных о некоторой предметной области.

Два варианта разработки:

- Продукт на продажу.
- Система под заказ.

Из чего состоит ИС: информация, программное обеспечение (ПО), аппаратное обеспечение («аппаратка»), персонал.

Виды ИС:

- Простая.
- Сложная: состоит из простых подсистем.
- Большая.

## 1.2. Система и её характеристики

*Фото 4, левая страница. Методичка, с. 5–6.*

**Система** — множество элементов, которые взаимодействуют между собой и образуют общее целое.

Что характеризует строение системы:

- **Элемент** — минимальная единица.
- **Компонент, подсистема** — относительно независимая часть системы со свойствами системы.
- **Связь, отношение** — ограничение степени свободы элементов.
- **Структура** — наиболее значимые компоненты и связи.
- **Цель** (на схеме без пояснения).

Что характеризует функционирование и развитие системы:

- **Состояние** — срез параметров системы.
- **Поведение** — как меняется состояние.
- **Развитие, эволюция**.
- **Жизненный цикл**.

## 1.3. Признаки сложной системы. Сложность ПО

*Фото 4, правая страница. Методичка, с. 6–7.*

Признаки сложной системы:

1. Иерархичность.
2. Можно выбирать, какие компоненты считать элементарными.
3. Связи внутри компонента сильнее, чем между компонентами.
4. Небольшое количество типов подсистем.
5. Сложная система получается в результате развития простой системы.

Почему ПО сложно:

1. Сложная предметная область.
2. Много разработчиков, сложно управлять разработкой.
3. Гибкость ПО.
4. Недетерминированность переходов между состояниями.

## 1.4. Архитектура ПО и ИС

*Фото 2, левая страница. Методичка, с. 7–8.*

**Архитектура ПО** — совокупность важнейших решений об организации программной системы:

- Выбор структурных элементов и их интерфейсов.
- Соединение элементов в более крупные системы.
- Архитектурный стиль.

**Архитектура ИС** — высокоуровневая концепция системы, учитывающая её окружение.

## 1.5. Классификация информационных систем

*Фото 2, левая страница. Методичка, с. 8–10.*

По архитектуре:

- Настольные.
- Распределённые: файл-серверные и клиент-серверные.

По количеству уровней программных компонентов:

- Одноуровневые.
- Двухуровневые.
- Трёхуровневые.

По характеру обработки данных:

- Информационно-поисковые системы.
- Информационные системы обработки данных.

По масштабу:

- Персональные.
- Групповые.
- Корпоративные.

## 1.7. Жизненный цикл ИС и его модели

*Фото 2 (справа) и 3 (слева). Методичка, с. 12–16.*

### Этапы жизненного цикла

1. Формирование и анализ требований.
2. Проектирование.
3. Разработка.
4. Тестирование.
5. Внедрение.

### Каскадная модель

Плюсы:

- Строгий порядок выполнения действий.
- Можно оценить качество на каждом этапе.

Минусы:

- Нет обратной связи между этапами.
- Не соответствует реальным условиям разработки.

### V-образная модель

- Левая ветвь (детализация проекта, сверху вниз): концепция → проектирование архитектуры → детальное проектирование.
- Внизу: реализация.
- Правая ветвь (тестирование и компоновка проекта, снизу вверх): модульное тестирование и интеграция → тестирование и проверка системы → введение в эксплуатацию.
- Между ветвями на схеме: «Проверка и утверждение». Время идёт слева направо.

### Итерационная модель

Сбор и анализ требований → проектирование → разработка → тестирование и развёртывание («деплой») → этап обзора → снова сбор и анализ требований.

### Спиралевидная модель

Пометка из тетради: чем она отличается от итерационной? В спиральной модели риски определяют содержание каждого витка.

Плюсы:

- Быстрое получение результата.
- Повышение конкурентоспособности.
- Устойчивость к изменчивым требованиям.

Минус: отсутствие регламентации стадий.

## 1.8. Стандарты разработки автоматизированных систем

*Фото 3, правая страница. Методичка, с. 16–17.*

1. **ISO/IEC 12207** — процессы жизненного цикла ПО.
2. **CMMI** (Capability Maturity Model Integration) — практики и рекомендации по управлению проектами.
3. **IEEE Standards** (Institute of Electrical and Electronics Engineers) — стандарты по разработке ПО.
4. **ГОСТ Р ИСО/МЭК 12207:2010** — жизненный цикл программных средств, на основе ISO/IEC 12207.
5. **ГОСТ Р 34.601-2013** — «Автоматизированные системы. Общие требования» (как записано в тетради и методичке; реквизиты стандарта отдельно не проверялись).

## 1.9. Техническое задание на разработку ИС

*Фото 3, правая страница. Методичка, с. 17–19.*

**Техническое задание (ТЗ)** — документ, описывающий требования и спецификации для проектирования, разработки и внедрения ИС.

Группы стандартов в ТЗ:

- Стандарты безопасности.
- Стандарты разработки и проектирования.
- Стандарты баз данных.
- Стандарты интерфейсов и протоколов.

Основные разделы ТЗ:

1. Введение.
2. Общие требования.
3. Архитектура системы.
4. Функциональные требования.
5. Нефункциональные требования.
6. Интерфейсы.
7. Тестирование.
8. Развёртывание и сопровождение.
9. График и бюджет.

## 1.10. Методы проектирования программных систем

*Фото 5. Методичка, с. 19–20.*

1. **Структурное проектирование:** декомпозируем систему на модули и определяем связи между ними.
2. **Объектно-ориентированное проектирование (ООП).**
3. **Компонентно-ориентированное проектирование.**
4. **UML** (язык моделирования, используемый при проектировании).
5. **Модельно-ориентированное проектирование:** создаём формальные модели системы, которые используются для автоматической генерации кода. Модели можно создавать с помощью DSL или SysML.

## 1.11. Методологии и документы на требования и спецификацию программных систем

*Фото 5. Методичка, с. 20–21.*

В постсоветской практике делают ТЗ по различным ГОСТам. В западной практике вместо одного документа делают разные документы для разных видов требований:

1. Бизнес-требования.
2. Пользовательские требования.
3. Функциональные требования.
4. Нефункциональные требования.
