# Раздел IV. Паттерны проектирования

Конспект по методичке `6sem_Proekt_Arkh_Is_Metodichka.pdf`, с. 64–144, с примерами из тренировки. Формулировки для контрольной опираются на методичку. Замечания про Rust показывают альтернативы, а не заменяют классическую схему.

## 4.1. Что такое паттерн и из чего он состоит

**Паттерн проектирования** — общая схема решения повторяющейся проблемы проектирования. Реализацию подбирают под задачу. Например, Наблюдатель задаёт роли издателя и подписчиков, но не требует хранить подписчиков именно в векторе или связном списке.

Четыре элемента описания (с. 64–65): **имя** (как называется), **задача** (когда применять), **решение** (какие роли и связи нужны), **результаты** (что выигрываем и какие принимаем компромиссы).

| Группа | За что отвечает | Примеры из методички |
| --- | --- | --- |
| Порождающие | Как создаются объекты | **Фабричный метод, Абстрактная фабрика, Одиночка, Строитель, Отложенная инициализация, Прототип** |
| Структурные | Как классы и объекты связаны и организованы | **Адаптер, Компоновщик, Декоратор, Фасад, Заместитель** |
| Поведенческие | Как объекты взаимодействуют и распределяют обязанности | **Команда, Итератор, Состояние, Стратегия, Посетитель, Шаблонный метод, Наблюдатель** |

- **Порождающие:** две фабрики; один экземпляр (Одиночка); сборка по шагам (Строитель); создание по необходимости (Отложенная инициализация); создание копированием образца (Прототип). Прототип ближе к `Clone`, чем к `Default`. Не путать **отложенную инициализацию** с **заместителем отложенного копирования**: первое откладывает создание или настройку объекта, второе откладывает создание отдельной копии.
- **Структурные:** согласовать интерфейсы (Адаптер), собрать дерево (Компоновщик), добавить поведение обёрткой (Декоратор), дать простой вход (Фасад), управлять доступом через представителя (Заместитель). Декоратор меняет поведение, но в классификации остаётся структурным.
- **Поведенческие:** упаковать запрос (Команда), обойти коллекцию (Итератор), реагировать по состоянию (Состояние), подставить алгоритм (Стратегия), добавить операцию над набором типов (Посетитель), переопределить шаги алгоритма (Шаблонный метод), уведомить подписчиков (Наблюдатель). Посетитель в методичке только назван: для списка достаточно помнить его группу. Как зацепка: `Circle.accept(visitor)` вызывает `visitor.visitCircle(this)`; новый формат экспорта добавляют отдельным посетителем, но новый тип фигуры потребует обновить посетителей.

### Где похожие решения расходятся

- **Фабричный метод и отдельная фабрика.** В классической схеме общий алгоритм вызывает `this.createTransport()`, а не `factory.createTransport()`. Абстрактная фабрика даёт один выбор для согласованного семейства: например, одна `WindowsFactory` даёт и Windows-кнопку, и Windows-чекбокс. Простая фабрика с `match` тоже может скрыть выбор продукта. В Rust `T::default()` или `T::create(...)` подходят, когда тип уже выбран; переданная функция подходит, когда способ создания задаёт вызывающий код. Классы-создатели ради одного конструктора не обязательны.
- **Стратегия и Состояние.** В схеме из методички стратегию выбирает и передаёт клиент. В State текущий объект определяет реакцию на событие и может инициировать переход. Реализовать новый класс состояния мало: нужен ещё достижимый переход в него. Для закрытого набора состояний можно оставить `match` и вынести каждую ветку в свою функцию.
- **Компоновщик и Наблюдатель.** В обоих возможен цикл по списку. Но группа фигур сама реализует интерфейс фигуры: её можно двигать и вкладывать в другую группу. Подписчик получает событие и не становится частью издателя. Группа слоёв наподобие Figma ближе к Компоновщику, чем рамка выделения. UML-композиция и паттерн Composite не одно и то же: ромб показывает владение частями. Если удаление группы удаляет оставшиеся внутри слои, уместен закрашенный ромб; возможность сначала разгруппировать слои этому не противоречит.
- **Адаптер и Фасад.** Адаптер подгоняет объект под интерфейс, которого клиент уже ждёт. Фасад упрощает работу с подсистемой. Например, фасад кинотеатра может запускать старый проигрыватель через адаптер.
- **Proxy и Декоратор.** По одному конструктору, наличию базового класса или факту делегирования отличить их нельзя. Прокси **представляет объект и управляет доступом**, декоратор **добавляет обязанности**, которые можно сочетать. Одна кеширующая обёртка может играть обе роли; пример с YouTube в методичке называется **кэширующим заместителем**. GoF прямо допускают, что защищающий заместитель может быть реализован как декоратор (с. 213 русского издания).

### Виды заместителей: термины методички (с. 129–133)

| Вид | По чему узнать |
| --- | --- |
| Удалённый | Локальный вызов превращается в обращение к объекту на другом сервере. |
| Логирующий | Ведёт историю обращений. |
| Фильтрующий | Пропускает разрешённые запросы к группе сетевых ресурсов. В ответе по методичке лучше «фильтрующий», а не «защищающий». |
| Умная ссылка | Выполняет дополнительные действия при обращении, например меняет счётчик ссылок. |
| Кэширующий | Отвечает из кеша вместо повторного вызова. Сервис может быть и локальным. |
| Синхронизирующий | Координирует доступ потоков; решает, **когда** пропустить вызов, а не **кому** это разрешено. |
| Упрощающий (фасадный) | Скрывает сложность **и управляет доступом** к набору классов. Обычный Фасад лишь даёт альтернативный интерфейс. |
| Виртуальный | Создаёт или загружает тяжёлый объект по необходимости. |
| Отложенного копирования | Подвид виртуального: отдельная копия появляется, когда она нужна. Пример: Copy-on-Write. |

## 4.17. Антипаттерны

**Антипаттерн** описывает распространённое решение, которое приводит к негативным последствиям. Разовая ошибка сама по себе не образует антипаттерн. Три группы из методички (с. 133–142): **разработка ПО, архитектура ПО, управление программными проектами**. В последней группе отдельного перечня примеров нет. Ниже примеры оставлены в тех группах, где их приводит методичка.

| Группа | Название | Как узнать |
| --- | --- | --- |
| Разработка | Большой двоичный объект | Почти все обязанности у одного объекта, остальные в основном хранят данные. По смыслу близко к God Object. |
| Разработка | Непрерывное устаревание | Трудно угнаться за обновлениями и сохранить совместимость версий. |
| Разработка | Поток лавы | В системе остался старый код, назначение которого забыли и который боятся трогать. |
| Разработка | Неоднозначная точка зрения | В модели смешаны разные точки зрения, например интерфейсы и детали реализации. |
| Разработка | Функциональная декомпозиция | Процедурный дизайн формально разложили по классам, не выделив осмысленные объекты. Обычная декомпозиция на функции сама по себе не ошибка. |
| Разработка | Полтергейсты | Короткоживущие классы с узкой ролью лишь запускают работу других объектов, не оправдывая отдельного класса. |
| Разработка | Лодочный якорь | Компонент не приносит пользы текущему проекту. |
| Разработка | Золотой молот | Одну знакомую технологию пытаются применить к самым разным задачам. |
| Разработка | Тупик | Команда изменяет неподдерживаемый сторонний компонент и сама несёт бремя его поддержки. |
| Разработка | Спагетти-код | Логику трудно проследить и непонятно, где безопасно её менять. |
| Разработка | Программирование «Вырезать и вставить» | Копипаст размножает одну логику; каждую копию приходится исправлять отдельно. |
| Разработка | Управление грибами | Разработчиков изолируют от пользователей, требования идут через посредников. |
| Архитектура | Автоматически генерируемая дымоходная труба | Локальные интерфейсы механически переносят в распределённую среду без пересмотра дизайна. |
| Архитектура | Предприятие-дымоход | В организации несколько изолированных систем без общего планирования. |
| Архитектура | Система дымохода | Внутри одной системы подсистемы соединены разовыми интеграциями «точка — точка». |
| Архитектура | Защищайте свои активы | Документы и процедуры множатся, а важные решения откладываются. |
| Архитектура | Привязка к поставщику | Поставщика трудно заменить, потому что его продукт встроен в систему и процессы. |
| Архитектура | Волчий билет | Продукт заявляет открытость, а реальные интерфейсы закрыты или расходятся со стандартом. |
| Архитектура | Архитектура по смыслу | Полагаются на интуицию и прошлые успехи вместо оценки рисков новой системы. |
| Архитектура | Тёплые тела | Команду комплектуют для численности, не учитывая нужные навыки. |
| Архитектура | Разработка комитетом | Коллективные решения приводят к перегруженной и несогласованной архитектуре. |
| Архитектура | Швейцарский армейский нож | Интерфейс класса пытается предусмотреть все сценарии и разрастается. |
| Архитектура | «Изобретите велосипед» (переизобретение колеса) | Пишут заново то, для чего уже есть готовое решение, не оценив альтернативы. |

Оговорки к списку: «Ошибку ввода» пропускаем. «Прогулку по минному полю», «Беспорядок» и «Великого старого герцога Йоркского» методичка описывает расплывчато или даёт расходящиеся трактовки; не использовать их как задания с единственным ответом. Для начала полезнее различать **Поток лавы и Лодочный якорь** (забытый код и бесполезный компонент) и **Большой двоичный объект и Швейцарский армейский нож** (слишком много обязанностей и слишком много операций интерфейса).

## 4.18. Составные (архитектурные) паттерны

**Составной паттерн** объединяет несколько паттернов для решения общей задачи. Основной пример методички (с. 142–144) — MVC. MVP и MVVM там описаны короче.

| Схема | Кто обрабатывает действие | Как View получает результат |
| --- | --- | --- |
| **MVC — Model–View–Controller** | Controller интерпретирует действие и даёт команду Model. | View отображает данные. В серверном варианте их можно передать шаблону; в классическом настольном MVC открытое View может наблюдать модель. |
| **MVP — Model–View–Presenter** | View сообщает о действии Presenter, тот обращается к модели. | В варианте с пассивным View Presenter явно вызывает метод экрана, например `showStatus()`. `P` означает **Presenter**, не Presentation. |
| **MVVM — Model–View–ViewModel** | View вызывает команду ViewModel, которая обращается к модели. | View привязывается к свойствам для экрана, например `statusText` и `canCancel`. ViewModel готовит их, но не рисует экран. |

**Model в MVC — роль, а не папка `models/`.** Модель представляет данные и правила работы с ними. `Order` может быть тонкой ORM-записью, а правило отмены может находиться в общем `CancelOrder` (Transaction Script). В таком случае оба выполняют работу Model. HTTP-контроллер принимает запрос, вызывает сценарий и формирует ответ. Если тот же сценарий можно запустить из фоновой задачи без HTTP, правило не привязано к контроллеру.

**Жизненный цикл View не отличает MVC от MVP и MVVM.** Сравнивай, кто готовит данные для экрана и как они до него доходят. В MVVM объект ViewModel может создать само окно или код навигации. В WPF `DataContext` указывает, где искать свойства и команды для привязок; сам он ничего не создаёт.
