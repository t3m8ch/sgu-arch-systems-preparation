# SOLID и GRASP

По презентации `SOLID_GRASP.pdf`: SOLID — слайды 6–74, GRASP — слайды 75–103.

**SOLID** помогает проектировать классы и их зависимости так, чтобы изменения затрагивали меньше кода. **GRASP** помогает решить, какому объекту поручить работу: кто знает нужные данные, кто создаёт объекты и кто координирует их действия.

## SOLID: пять принципов

| Принцип | Определение и пример |
| --- | --- |
| **S — Single Responsibility Principle (SRP), единственная ответственность** | У класса или модуля должна быть одна причина для изменения. У `Order` могут быть методы для работы с позициями и расчёта суммы, но сохранение и печать меняются по своим причинам, поэтому их выносят в репозиторий и отдельный класс печати. |
| **O — Open–Closed Principle (OCP), открытость/закрытость** | Код открыт для расширения и закрыт для модификации. Новый канал отправки добавляют отдельной реализацией `SendingStrategy`, не переписывая `MessageSender`. |
| **L — Liskov Substitution Principle (LSP), подстановка Лисков** | Подтип должен заменять базовый тип без нарушения его контракта. Если `Employee` обещает вернуть сведения о работе, `JuniorEmployee` не должен вместо этого бросать `NotImplementedException`. |
| **I — Interface Segregation Principle (ISP), разделение интерфейсов** | Клиент не должен зависеть от методов, которыми не пользуется. Вместо общего интерфейса с `work()`, `eat()` и `sleep()` выделяют отдельные интерфейсы. Робот реализует только `Workable`. |
| **D — Dependency Inversion Principle (DIP), инверсия зависимостей** | Высокоуровневая логика и низкоуровневые реализации зависят от абстракции; абстракция не зависит от деталей. `Switch` работает с `Switchable`, а лампа и вентилятор реализуют этот контракт. |

## GRASP: девять шаблонов распределения ответственности

*General Responsibility Assignment Software Patterns*. Ответственность объекта может состоять в том, чтобы **знать** что-то или **делать** что-то.

### Основные

| Шаблон | Кому поручить работу |
| --- | --- |
| **Information Expert (Информационный эксперт)** | Тому, у кого уже есть нужные данные. `Customer` знает свои заказы и может сложить их суммы. |
| **Creator (Создатель)** | Тому, кто содержит, учитывает или использует создаваемые объекты либо знает данные для их инициализации. `Customer` создаёт `Order` и добавляет его в список заказов. |
| **Controller (Контроллер)** | Входное системное событие принимает объект, представляющий всю систему или отдельный сценарий. При сканировании товара `Register` просит каталог найти товар, а текущую продажу — добавить позицию. Он координирует работу, а не выполняет её за эти объекты. |
| **Low Coupling (Слабая связанность)** | Сокращай число и силу зависимостей **между** классами, чтобы замена одного класса реже требовала правок в других. |
| **High Cohesion (Высокая связность)** | Держи **внутри** класса обязанности, которые служат одной цели. Например, печать и хранение не нужно собирать в классе, который рассчитывает сумму заказа. |

### Дополнительные

| Шаблон | Как применить |
| --- | --- |
| **Pure Fabrication (Чистая выдумка)** | Введи класс, которого нет в предметной области, если техническая работа нарушит фокус существующего класса. `CustomerRepository` загружает и сохраняет клиентов, а `Customer` не знает деталей базы. |
| **Indirection (Посредник)** | Если прямая зависимость нежелательна, поручай связь промежуточному объекту. Контроллер отправляет команду через `IMediator`, а тот находит нужный обработчик. Если посредник лишь перенаправляет вызов стабильного `IOrdersService`, прямой вызов проще. |
| **Polymorphism (Полиморфизм)** | Поручай различающееся поведение самим типам через общий контракт. `Square` и `Circle` по-разному выполняют один и тот же вызов `render()`. |
| **Protected Variations (Устойчивость к изменениям)** | Найди вероятную точку изменений и скрой её за стабильным контрактом. Например, `SendingStrategy` скрывает различия между каналами отправки от `MessageSender`. |

**Как различать похожие принципы.** SRP спрашивает, почему класс придётся менять, а High Cohesion — насколько близки его обязанности. DIP задаёт направление зависимостей, а Low Coupling оценивает их число и силу. GRASP и SOLID помогают обосновать решение: если дополнительный класс не изолирует отдельную обязанность или зависимость, вводить его только ради принципа не нужно.
